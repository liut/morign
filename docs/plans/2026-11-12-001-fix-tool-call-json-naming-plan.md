# fix: 对外报文的工具调用字段改用驼峰命名

## Summary

对外响应结构体 `api.ChatMessage` 的 11 个字段里有 9 个是驼峰（`id` / `delta` / `text` / `think` / `role` / `name` / `finishReason` / `csid` / `title`），只有 `tool_calls` 与 `tool_call_id` 是 OpenAI 协议原样搬过来的下划线——同一个结构体里混了两套命名风格，客户端也跟着写成 `tool_calls`。本次把这两个对外字段改成驼峰，并同步重新生成接口文档。

**不动与 LLM provider 交互的字段名**：`pkg/services/llm/types.go` 的 `Message` 必须保持 OpenAI 兼容的 `tool_calls` / `tool_call_id`，改了会直接打断模型调用。两处同名字段是本计划最容易误改的地方。

---

## Problem Frame

`pkg/web/api/convo_basic.go:37-53`：

```go
// for response to client
type ChatMessage struct {
	ID    string `json:"id,omitempty"`
	Delta string `json:"delta,omitempty"`
	Text  string `json:"text,omitempty"`
	Think string `json:"think,omitempty"`
	Role  string `json:"role,omitempty"`
	Name  string `json:"name,omitempty"`

	// For Role=assistant prompts this may be set to the tool calls generated by the model, such as function calls.
	ToolCalls []map[string]any `json:"tool_calls,omitempty"`

	// For Role=tool prompts this should be set to the ID given in the assistant's prior request to call a tool.
	ToolCallID string `json:"tool_call_id,omitempty"`

	FinishReason string `json:"finishReason,omitempty"`

	ConversationID string `json:"csid,omitempty"`

	Title string `json:"title,omitempty"`
}
```

`tool_calls` / `tool_call_id` 是从 OpenAI chat completion 的消息体原样搬过来的，连注释一起。而这个结构体的其余字段是本项目自己的驼峰风格。`AGENTS.md` 的编码规范写着「修改结构体时注意 JSON tag 命名一致」——同一结构体内部不一致，正是这条规范要防的情况。

字段的写入点在 `pkg/web/api/handle_convo.go:292-293`：

```go
if len(event.ToolCalls) > 0 && event.StopReason == llm.FinishReasonToolCalls {
	cm.ToolCalls = convertToolCallsForJSON(event.ToolCalls)
}
```

即 SSE 流中带 `finishReason: "tool_calls"` 的那条消息，其调用数组就来自这个字段。客户端 Calisyn 前端因此把协议字段写成 `tool_calls`（`src/api/index.ts` 的 `StreamMessage.tool_calls`），并在解析处按 `data.tool_calls` 取值——命名分裂沿着协议一路传导到了客户端的类型定义。

另需注意 `finishReason` 的取值里也有一个 `tool_calls`（`pkg/services/llm/types.go:18` 的 `FinishReasonToolCalls = "tool_calls"`）。那是**值**不是字段名，与本次改动无关，保持原样。

本次修订由客户端侧提出：Calisyn 前端要把工具调用相关命名统一到驼峰，前端是协议的下游，先改后端才能让两端收敛到同一套命名。

## Requirements

**对外协议**

- R1. `api.ChatMessage` 的 `tool_calls` 改名为 `toolCalls`、`tool_call_id` 改名为 `toolCallID`，与同一结构体的其余字段保持驼峰一致。
- R2. 工具调用数组的**内部结构**不变：`id` / `type` / `function`（含 `name` / `arguments`）保持现状，客户端的解析逻辑不需要跟着改内部结构。
- R3. 与 LLM provider 交互的请求体字段名不变：`pkg/services/llm/types.go` 中 `Message` 的 `tool_calls` / `tool_call_id` 是 OpenAI 兼容格式，必须保持下划线。
- R4. 内部持久化与审计结构不变：`pkg/services/llm/types.go`、`pkg/services/llm/audit.go` 等落库 / 落审计日志的 JSON 字段名不动，避免历史数据解析断裂。该约束由 `pkg/services/llm/types_test.go` 的回归测试守住（断言 `llm.Message` 序列化后仍是下划线键、驼峰键不存在）。
- R5. 接口文档同步：`docs/swagger.json` / `docs/swagger.yaml` 中 `api.ChatMessage` 的字段名随之更新，由 `make gen-apidoc` 重新生成，不手改生成物。

**兼容与发布**

- R6. 客户端（Calisyn）需要同步改解析字段名；两个仓库独立发布，直接改名会让仍在跑的旧前端静默丢失工具调用（该能力刚在 Calisyn 侧修复上线）。
- R7. 兼容期策略：后端在过渡版本同时下发 `toolCalls` 与 `tool_calls`（前者为准，后者临时保留），Calisyn 前端切到读驼峰字段后再由后端移除下划线字段。
- R8. 过渡期结束（Calisyn 已全部升级到读驼峰字段）后，移除 `tool_calls` 的双写过渡字段。收尾动作见 U2 的收尾清单——注意驼峰的 `toolCallID` 字段**保留**，只摘下划线别名。

- 不改会话持久化的表结构与数据。

## Key Technical Decisions

- **只改对外协议层的那一处 json tag**：`api.ChatMessage` 是响应结构体，改它不影响任何内部链路；provider 兼容层与持久化层保持原样，调用链零风险。
- **`tool_call_id` 一并改名**：该字段在响应方向实际不会出现（客户端不直接发 tool 消息，agent 循环在后端），但留在同一个结构体里的两个下划线字段会让「命名不一致」的问题继续存在；改名是一行的事，不改名则问题留着。
- **不改 `finishReason` 的取值**：`tool_calls` 作为一个**值**（`FinishReasonToolCalls`）与字段名无关，改它会牵动 provider 解析与客户端判定，明确划在范围外。
- **过渡期双写而不是硬切**：两个仓库独立发布，硬切会让未升级的前端静默丢掉工具调用——而这正是刚修复的能力。双写一个版本，前端切换后再摘除，代价是两个字段并存一小段时间，收益是没有静默故障窗口。
- **`toolCalls` 为准、`tool_calls` 为过渡字段**：双写时两个字段内容相同，客户端只应依赖 `toolCalls`。

## Implementation Units

### U1. 对外字段改名

**Goal:** `api.ChatMessage` 的两个下划线字段改为驼峰，并让接口文档同步。

**Requirements:** R1, R2, R3, R4, R5

**Dependencies:** None

**Files:**
- Modify: `pkg/web/api/convo_basic.go`
- Regenerate: `docs/swagger.json`, `docs/swagger.yaml`

**Approach:**
- `ToolCalls []map[string]any` 的 tag 改为 `json:"toolCalls,omitempty"`，`ToolCallID string` 的 tag 改为 `json:"toolCallID,omitempty"`，字段名与注释保持不变。
- 结构体内部的赋值点（`handle_convo.go:293`）不需要改——Go 字段名没变，只变序列化后的键名。
- 跑 `make gen-apidoc` 重新生成接口文档，核对 `api.ChatMessage` 下出现 `toolCalls` / `toolCallID`，且 `tool_calls` / `tool_call_id` 不再出现在该定义里。
- 确认 `api.ChatRequest` 等其他定义未受影响（它们本来就没有这两个字段）。

**Patterns to follow:**
- `pkg/web/api/convo_basic.go` 同文件其他结构体的驼峰 tag 写法

**Test scenarios:**
- Happy path: `make vet`、`make lint`、`make test-models` 通过；`pkg/web/api` 的既有单测（含 `TestConvertToolCallsForJSON`）不受影响。
- Integration: 跑一次带工具调用的会话，抓 SSE 报文确认键名为 `toolCalls`，且数组内部仍是 `id` / `type` / `function`。

**Verification:** `make vet && make lint` 通过；`make gen-apidoc` 后 swagger 中 `api.ChatMessage` 的字段名与结构体一致。

---

### U2. 兼容期双写与过渡收尾

**Goal:** 覆盖后端先发、前端后升的发布顺序，避免旧客户端静默丢失工具调用。

**Requirements:** R6, R7, R8

**Dependencies:** U1

**Files:**
- Modify: `pkg/web/api/convo_basic.go`
- Modify: `pkg/web/api/handle_convo.go`（构造响应处）
- Modify: `pkg/web/api/convo_basic_test.go`（新增，协议与双写断言）

**Approach:**
- 双写实现有两种形态，选其一：
  - 在 `ChatMessage` 上加一个仅用于序列化的过渡字段 `ToolCallsLegacy []map[string]any \`json:"tool_calls,omitempty"\``，与 `ToolCalls` 同时赋值；
  - 或在写出 SSE 的地方手写一层 map 补上旧键。
  - 采用前者：序列化行为留在结构体里，写出层不掺协议兼容逻辑。
- 写入收敛到两处，避免别名字段被漏写：
  - `ChatMessage.setToolCalls` 同时赋 `ToolCalls` 与 `ToolCallsLegacy`；
  - `handle_convo.go` 的工具调用装配点收敛为 `applyToolCalls(cm, event, csid)`，新增写入点必须走它。
- 双写期间 `toolCalls` 与 `tool_calls` 内容完全相同，客户端只应依赖 `toolCalls`——**只读 `toolCalls`，不要两个键都读再合并**，否则工具调用会渲染两遍。
- 收尾条件：Calisyn 前端全部升级到读 `toolCalls` 之后，执行下面的收尾清单，并把「过渡期已结束」写进本计划的状态与变更记录。

**收尾清单**（过渡期结束时按序执行）：

1. 删除 `ChatMessage.ToolCallsLegacy` 字段。
2. 删除 `ChatMessage.setToolCalls` 的别名赋值；`applyToolCalls` 改为直接赋 `cm.ToolCalls`（`setToolCalls` 可整体删除，写入点改回直接赋值）。
3. **保留** `ToolCallID`（驼峰 `toolCallID`）字段不动。
4. 改写 `pkg/web/api/convo_basic_test.go` 中依赖 `tool_calls` 存在的断言：改为只断言 `toolCalls` 存在、且 `tool_calls` 不存在。`pkg/services/llm/types_test.go` 的 provider 侧断言不动。
5. 同步更新 `docs/swagger.json` / `docs/swagger.yaml`（再次 `make gen-apidoc`）。
6. 跑 `make vet` 与 `make lint`。

**Patterns to follow:**
- `pkg/web/api/convo_basic.go` 中 `omitempty` 的使用方式（过渡字段同样需要 `omitempty`，避免每次响应都多出空字段）

**Test scenarios:**
- Happy path: 双写版本下，SSE 报文同时含 `toolCalls` 与 `tool_calls`，两者内容一致。
- Edge case: 没有工具调用的普通消息，两个字段都不出现（`omitempty` 生效）。
- Integration: 旧版 Calisyn 前端（只读 `tool_calls`）在双写期间仍能正常渲染工具调用。

**Verification:** 用新旧两个前端分别连一次，确认工具调用都能渲染；收尾版本抓包确认只剩 `toolCalls`。

## System-Wide Impact

- **Interaction graph:** 对外协议字段 → SSE 报文 → Calisyn 前端 `StreamMessage` 类型与解析处 → 前端渲染。任一环没跟上，表现为「工具调用不显示」而不是报错，属于静默故障。
- **Error propagation:** 不涉及错误路径变化；双写期间两个键内容一致，不存在取值分歧。
- **State lifecycle risks:** 持久化与审计的字段名不变，历史数据解析不受影响；若误改了 `pkg/services/llm/types.go`，会直接打断模型调用（请求体字段名不再被 provider 接受）。
- **API surface parity:** `api.ChatMessage` 同时出现在 SSE 响应与接口文档中，两者由 `make gen-apidoc` 保证一致。
- **Integration coverage:** 需要与 Calisyn 一起联调，确认新旧两端在双写期都能正确渲染。
- **Unchanged invariants:** provider 请求体、持久化表结构与数据、SSE 事件格式与顺序、工具执行链路。
